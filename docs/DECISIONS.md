# Decisions

Non-obvious choices and their trade-offs, dated, newest section first. Read the relevant entry before changing a mechanism that looks odd. Choices made autonomously under a delegation are recorded here for the user to review; an entry is a record, not a claim that the capability is complete.

## 2026-11-02

| Decision | Reason and trade-off |
| --- | --- |
| The composite Action uses hash-locked wheels and an isolated Python launcher loading Partlet from the selected Action checkout. uv and gitleaks downloads have version and checksum pins; setup disables uv configuration and caching. | The publisher holds R2 write credentials, so dependencies and code must not resolve from the private source checkout or its tool configuration. Python import settings are also cleared for child tools. The source checkout receives no package installation. Cost: dependency changes require regenerating and reviewing the Action lock; supported runners are Linux x64 and ARM64. |
| Only pack and index URLs are immutable. Stable site, raw and archive URLs use a 60-second cache with ETags, even though their stored keys contain a build or tip. | Public URLs resolve through `current`; caching those URLs as immutable would hide later publications. Cached Git metadata is safe only while advertised objects remain available; the publisher's separate timed pack policy supplies that window. |
| Retain pack/index objects for at least an hour from the first sweep observing them outside both live and previous pack lists. Persist retirement timestamps before deletions, reuse them on retries and unchanged runs, and clear them for revived objects. | One publication of grace can disappear inside the Worker's 60-second metadata freshness. An hour reserves 59 further minutes for an in-flight fetch, including rapid consolidations; disabling metadata caching alone does not protect it. Orphan uploads get the same conservative timer because interruption can obscure their publication status. Cost: storage temporarily retains obsolete packs and cleanup needs a later run; clock rollback delays cleanup. Corrupt state fails closed. Explicit unpublish deliberately invalidates active clients and removes all retained objects. |
| Evaluate HTTP entity-tag conditions in the Worker instead of forwarding request conditions wholesale to R2. | R2 returns bodiless objects for several failed conditions; treating all of them as 304 is incorrect. Strong If-Match precedes weak If-None-Match; pack ranges respect If-Range and GET semantics. Date validators are omitted because responses do not provide Last-Modified. |
| Disable Miniflare's Cloudflare metadata fetch explicitly in local validation. | `wrangler dev --local` alone does not disable its default metadata lookup. Tests, smoke, bundle/type gates and documented preview commands turn it off in addition to disabling metrics and using local bindings. |
| LocalStore listing hides only temporary files allocated by its active writes, identified by filesystem identity while their temporary names still exist. | A basename prefix also hides committed `.partlet-tmp-*` content from retirement cleanup. Tracking actual allocated files preserves all content names without changing keys, reserving a namespace, requiring a writable parent of the store root, or crossing filesystem boundaries during atomic replacement. After replacement the destination is immediately listable; abandoned temporary files are listable orphan sweep candidates. Publication remains serialized, and active temporary tracking is local to one Store instance. |
| Before local publication uploads or its unchanged shortcut, probe all rendered site keys in a temporary directory on the output filesystem and reject aliased file or directory identities. | Case and Unicode normalization rules depend on the volume. UTF-8 validation alone cannot stop distinct Git paths from overwriting each other's raw or blob content. Probing every path component also catches aliased directories and file/directory conflicts. Storage keys and the Store protocol stay unchanged for static HTTP and the planned Worker. Cost: render and create empty probe paths even on unchanged builds; names the local filesystem cannot distinguish must be renamed before a local build. |

## 2026-10-26

| Decision | Reason and trade-off |
| --- | --- |
| Reject export-tip file paths that are not valid UTF-8 before any project uploads, pointer changes or unchanged-build shortcut. | Git paths are bytes, but site keys, HTML and URLs use Unicode. Replacement decoding merges distinct byte paths and silently overwrites site output. Strict decoding reports the offending byte path so it can be renamed; valid Unicode, including a literal replacement character, remains supported. Cost: non-UTF-8 tip paths block the project's publication, and unchanged runs read the tip's blobs to validate paths. Historical paths outside the tip are not subject to this site check. |
| Directory page keys join the original path segments with `/children/`, then append `/index.html` under `tree/`. Public URLs keep the original directory path. | A page at `tree/docs/index.html` cannot also be a filesystem ancestor of the page for `docs/index.html`. The child namespace makes that page `tree/docs/children/index.html/index.html`. A repository directory named `children` is still an ordinary name, separated from the next level by another `children` namespace. This avoids percent-encoding differences between Python and JavaScript and does not lengthen individual filename components; the cost is extra path depth and total key length. The future Worker lookup in the Worker plan uses the same mapping. |
| The site build ID also hashes a storage-layout identifier. | Changing the page layout must re-render an unchanged export into a new build, rather than take the unchanged shortcut or overwrite an earlier immutable build. Existing packs stay unchanged and the earlier build keeps its usual one-publish grace period. |

## 2026-10-17

| Decision | Reason and trade-off |
| --- | --- |
| Every CLI build, publish and unpublish holds a per-source lock created with `If-None-Match: *`; automation must also serialize runs by source. Locks never expire automatically and `partlet unlock` is explicit recovery. | Cleanup deletes keys no live or grace pointer names, including another publisher's unfinished uploads. Workflow concurrency covers only that workflow/repository; the lock covers other callers. A retried conditional put recognizes its own token. R2 has no conditional delete, so deletes use one request attempt: an uncertain result raises instead of retrying against a replacement lock. Verify the holder has stopped before unlocking; removing a live holder still permits a read/delete race. |
| R2 uses boto3's S3 API with checksum calculation/validation only when required, and only `NoSuchKey` means absence. | This follows Cloudflare's Python client example while keeping checksum behavior independent of SDK defaults. `NoSuchBucket` is also a 404 and must remain an error. Reads retry failed streams and close every response. Lists follow all continuation tokens. Deletes never retry an unknown outcome. |
| R2 settings come from `PARTLET_R2_*`; access keys leave the environment before any child process starts. Endpoints require HTTPS except loopback simulation. | Git, filter-repo and gitleaks never inherit the publisher's access keys. Embedded URL credentials and server error text are not echoed. Explicit credentials avoid ambient SDK credential selection. |
| `partlet publish` requires HEAD at the local publishing branch tip and a manifest identical to the committed file. | Exports read the branch, while approval pins come from the working tree. Matching both prevents publication with uncommitted approvals or a feature-branch manifest. Previews remain available through `build`. |
| Scan each export's full reachable history with gitleaks on every run that uploads, before the first project write. | An approval pin cannot prove a review scan happened or which configuration it used. Full-history scanning prevents approval from bypassing a finding anywhere in the exported history. Cost: scan time grows with project history, and a rule or allowlist change can block an earlier publication; accept false positives in `.gitleaks.toml` or `.gitleaksignore`. |
| gitleaks is pinned to one release by SHA-256 per platform, run with `--exit-code 0 --redact`, and findings are read from its JSON report. | Exit status 1 can mean findings or an error, so a nonzero exit must fail the scan while findings come from the report. Redaction keeps secrets out of reports and results; tool-error stderr is omitted because configuration errors may echo values. Missing, malformed or stale reports fail closed. A version bump changes the pin and platform hashes in a separate PR. |
| git-filter-repo is pinned exactly in `pyproject.toml`, and tool checks refuse another installed version. Git has a minimum version and its actual version is recorded. | Export commit hashes depend on filter-repo's behaviour, including empty move commits. The Git check enforces the required command interfaces; it does not prove identical output across Git versions. |
| gitleaks uses `--diff-merges=first-parent` while traversing every reachable commit, with global and system Git configuration disabled. | Ordinary patches preserve canonical paths for custom rules and allowlists, including conflict resolutions and octopus merges. Remerge output can add a spurious `b/` prefix and suppress path-based detection. Traversal's `--first-parent` is forbidden because it hides secrets deleted on side branches before merging. A secret can have separate native fingerprints at its origin and importing merges; accepted findings need every reported fingerprint. Git stays at the existing 2.31 floor. |
| `partlet review` reads the published tip from the public site (`<base_url>/<name>/info/refs`), not from R2. | Review needs no R2 credentials on the user's machine. `--published-tip` covers a site that is unreachable or not yet deployed. |
| Review refuses to approve while gitleaks reports findings, or a non-fast-forward tip without `--allow-rewrite`. | Publishing would refuse either case; rejecting the approval keeps an unusable pin out of `partlet.toml`. The report covers deleted paths, large historical files, authors, committers, commit messages and possible undeclared earlier locations. |
| Approval edits preserve TOML layout and comments and replace the manifest atomically after validating the result. | A malformed edit or a changed manifest leaves the original untouched. Interactive review checks that the manifest still matches the report before writing the pin. |
| A publish ends by sweeping the project's packs, site builds and archives: it lists those prefixes and deletes every key that neither the live pointers nor the publish before them name. `current` records that earlier publish's build, tip and pack list as `previous`, and the `unchanged` shortcut runs the same sweep. This replaces `cleanup.json`; since 2026-11-02, packs also have the timed grace recorded above. | A list of superseded keys written after `current` is lost when a publish dies between the two, and nothing ever listed what a publish uploads before it dies. Diffing the stored keys against the pointers needs neither list, and keeping the grace record inside `current`, the last pointer written, means the grace set moves exactly when the live build does. Superseded keys still get one publish of grace: an `unchanged` run keeps them and the next publish that moves `current` deletes them; orphans from an interrupted publish go at the next run. Cost: every run lists the three prefixes, a few list requests per project on R2, and nothing else may be stored under them, because any key there that no pointer names is deleted. Publishes must not overlap, since a sweep would delete another run's uploads before that run names them: the workflow's `concurrency` group serialises CI runs, and local `partlet build` runs into the same directory must not overlap either. |
| A publish that drops packs (consolidation or rewrite) first writes `objects/info/packs` listing the old and new packs together, then moves `info/refs` and `HEAD`, then writes the final list. | Writing the short list first left refs naming objects in no listed pack if the publish died before `info/refs` moved; if the rewrite was then abandoned, the next `unchanged` run's sweep deleted the old pack and the repository could not be cloned. With the combined list every intermediate state is clonable and the sweep keeps every listed pack. Cost: a publish that dies after `info/refs` but before the final list leaves the old packs listed, and stored, until the next consolidation or rewrite drops them; a rewrite that dies before `info/refs` and is then abandoned leaves its unused new pack listed, and stored, the same way. |

## 2026-10-15

| Decision | Reason and trade-off |
| --- | --- |
| Export never passes `--force` to `git filter-repo`, and checks that its destination is a fresh bare repository of its own before every mutating command. | filter-repo rewrites every ref and then expires reflogs and repacks, so running it against the wrong repository loses unpushed work for good. Without `--force` filter-repo refuses anything that does not look like a fresh clone, and partlet's own check refuses any destination that is not a bare repository at exactly that path, outside the monorepo. Cost: about twenty short `git rev-parse` calls per export. A `[remote]` section in the user's global or system git config makes filter-repo refuse the export; it fails closed. |
| The site build ID hashes the export tip, the project description, the site `base_url`, the Partlet version and, since 2026-10-26, a storage-layout identifier. | The spec names only the tip and version, but the description and `base_url` (in the clone URL) are rendered into the pages, so changing either must produce a new build instead of taking the `unchanged` shortcut. Cost: a manifest edit to either re-renders the project. |
| Site/archive keys superseded by a publish are deleted by the next publish, not by the one that superseded them; packs additionally use timed grace since 2026-11-02. | Gives clients in the middle of a fetch or page load one publish of grace before old packs, site builds and archives disappear. The bookkeeping was a `cleanup.json` list of superseded keys until 2026-10-17, when a sweep replaced it (see that entry). |
| A directory move can leave an empty move commit in the export. | The spec expects filter-repo to prune the move commit as empty, and it does for plain file names. When the moved directory holds a name that fast-export quotes (spaces, non-ASCII), filter-repo keeps the move as an empty commit. The export still fast-forwards and earlier hashes are unchanged. A filter-repo release that changes this would change export hashes, so publishing (plan 3) must pin filter-repo exactly. |
| Export project history with `git filter-repo`, not `git subtree split`. | `subtree split` follows one prefix only, so a directory move loses all earlier history and turns into a rewrite. `filter-repo` maps the current and previous paths to the root, so a move made after publication fast-forwards. Cost: one extra dependency, installed with pip and pinned. |
| A project publishes only after its export tip is pinned as `approved` in the manifest, and every later publish must fast-forward from the published tip. | The pin records the user's review of the full history (deleted files, authors, messages, secret scan) and anchors the rewrite check, so CI can enforce both. A rewrite needs `allow_rewrite_of` naming the exact published tip, which lets exactly one rewrite through. |
| Pre-render the whole site in the publisher; the Worker only maps URLs to stored objects. | Keeps all rendering in tested Python and the Worker small. Cost: template changes need a re-run of the publisher, which re-renders from existing exports without touching Git history. |
| One source monorepo per site, with every store key under a per-source prefix. | Simplest model for one user. The prefix leaves room for several sources on one site without changing the storage layout. |
| Shell hooks in a tracked `.githooks/` directory rather than a hook manager. | No dependency to install, and today's gates are shell scripts. Revisit when the Python and TypeScript gates make a polyglot manager such as lefthook worth it. |
