# Decisions

Non-obvious choices and their trade-offs, dated, newest section first. Read the relevant entry before changing a mechanism that looks odd. Choices made autonomously under a delegation are recorded here for the user to review; an entry is a record, not a claim that the capability is complete.

## 2026-10-15

| Decision | Reason and trade-off |
| --- | --- |
| Export never passes `--force` to `git filter-repo`, and checks that its destination is a fresh bare repository of its own before every mutating command. | filter-repo rewrites every ref and then expires reflogs and repacks, so running it against the wrong repository loses unpushed work for good. Without `--force` filter-repo refuses anything that does not look like a fresh clone, and partlet's own check refuses any destination that is not a bare repository at exactly that path, outside the monorepo. Cost: about twenty short `git rev-parse` calls per export. A `[remote]` section in the user's global or system git config makes filter-repo refuse the export; it fails closed. |
| The site build ID hashes the export tip, the project description, the site `base_url` and the Partlet version. | The spec names only the tip and version, but the description and `base_url` (in the clone URL) are rendered into the pages, so changing either must produce a new build instead of taking the `unchanged` shortcut. Cost: a manifest edit to either re-renders the project. |
| Keys superseded by a publish are listed in the project's `cleanup.json` and deleted at the start of the next publish, not at the end of the one that superseded them. | Gives clients in the middle of a fetch or page load one publish of grace before old packs, site builds and archives disappear. Cost: keys uploaded by a publish that dies before writing `cleanup.json` are never listed, so they stay until a sweep exists (`publish-orphan-sweep` in `TODO.md`). |
| A directory move can leave an empty move commit in the export. | The spec expects filter-repo to prune the move commit as empty, and it does for plain file names. When the moved directory holds a name that fast-export quotes (spaces, non-ASCII), filter-repo keeps the move as an empty commit. The export still fast-forwards and earlier hashes are unchanged. A filter-repo release that changes this would change export hashes, so publishing (plan 3) must pin filter-repo exactly. |
| Export project history with `git filter-repo`, not `git subtree split`. | `subtree split` follows one prefix only, so a directory move loses all earlier history and turns into a rewrite. `filter-repo` maps the current and previous paths to the root, so a move made after publication fast-forwards. Cost: one extra dependency, installed with pip and pinned. |
| A project publishes only after its export tip is pinned as `approved` in the manifest, and every later publish must fast-forward from the published tip. | The pin records the user's review of the full history (deleted files, authors, messages, secret scan) and anchors the rewrite check, so CI can enforce both. A rewrite needs `allow_rewrite_of` naming the exact published tip, which lets exactly one rewrite through. |
| Pre-render the whole site in the publisher; the Worker only maps URLs to stored objects. | Keeps all rendering in tested Python and the Worker small. Cost: template changes need a re-run of the publisher, which re-renders from existing exports without touching Git history. |
| One source monorepo per site, with every store key under a per-source prefix. | Simplest model for one user. The prefix leaves room for several sources on one site without changing the storage layout. |
| Shell hooks in a tracked `.githooks/` directory rather than a hook manager. | No dependency to install, and today's gates are shell scripts. Revisit when the Python and TypeScript gates make a polyglot manager such as lefthook worth it. |
